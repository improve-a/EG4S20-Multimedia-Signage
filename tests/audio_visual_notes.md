# Audio visualization and shared-reader acceptance

`audio_visualizer` consumes the actual HDMI-selected PCM24 sample stream in the 25MHz pixel/audio clock domain. Every 64 valid samples, it stores signed left/right samples scaled by arithmetic shift 18 in one 256x14-bit synchronous-read history RAM. At 48kHz this gives 750 points/second and a ~0.341-second full history. The unfilled portion is dark with a center line and never reads uninitialized history. RAM contents are not reset; pointer/count reset invalidates them. Newest points are right-aligned before full, then the oldest point is at the current write pointer. L is green, R is blue, overlapping zero is white. Wave panel is x16..527, y320..415, center y368; signed extrema -32/+31 map to y400/y337. Peak bar x16..527, y428..439 scales magnitude 0..32768 to width 0..512 by a six-bit shift, without multiplication. Status text is x16..79, y304..317: W:HEX, except B is labelled TONE to identify no-WAV fallback.

All RGB/HS/VS/DE outputs pass through the same two registers. `enable=0` preserves original RGB including blanking pixels with that same delay. History still records when the overlay is hidden. Place the module after color adjustment and before the existing OSD; ticker y450 and progress y468 remain outside the new regions. History is live, so a point may change during a displayed frame. `peak` must represent the selected PCM source if a fallback source is desired in the bar; history always reflects the sample inputs.

Fresh Windows Icarus test `audio_visual_001` passed 1,917,260 pipeline/pixel checks in 37.765 wall seconds. Coverage: bypass and matching HS/VS/DE delay; never-written history; every-64-sample selection; partial history alignment; 300-point ring ordering/wrap; signed extrema and full zero history; bar empty/half/full; W:HEX and TONE glyph bits. Source SHA256: `cbd6cee09c75e3670c06c81bedc8c038d41d8b36dd648d5bb5b16f5c1fcabc0c`.

Shared-reader test `audio_arbiter_003` connects the frozen real audio_media/parser/FIFO/player to media_sector_arbiter and a saturated BMP client. It supplies actual WAV sector bytes, including scanning empty LBA0/1 and a RIFF at LBA2 whose 513-byte JUNK chunk crosses sectors. The physical transport model uses at least 64 system clocks per SD byte (12.5Mbit/s SPI at 100MHz system clock), 2048 clocks command overhead and CRC delay before the sector completion. It checks stable physical request/LBA throughout each transaction and each routed BMP 512-byte count. All 2304 stereo PCM frames are checked sample-by-sample for exact signed L/R order.

`audio_arbiter_003`: PASS, 89.984 wall seconds, 53.64668ms simulated time, 24 audio sectors and 129 BMP sectors, no FIFO underflow/overflow or PCM loss/duplication. Longest audio request-to-grant delay was 34889 system clocks = 348.89us. Longest sector was 34881 clocks = 348.81us. Including the arbiter drain, modeled full payload throughput is approximately 1.46MB/s; even ordinary 1:1 round-robin gives audio about 0.73MB/s, versus stereo PCM16/48k demand 192000 bytes/s (approximately 3.8x headroom). The 512-frame audio prefill stores 10.67ms, over 30x this measured maximum grant delay. These are model-specific RTL results, not measured physical-card service guarantees.

Earlier audio_arbiter_001/002 attempts timed out at 120s because the first testbench sampled completion on the wrong edge and its SD model delayed after completion until after the request-low drain interval, which prevented another transaction. Corrections are confined to the testbench: clients sample end on posedge, CRC delay precedes end, and the physical model returns idle when it sees request low. All original attempts and logs are retained. No frozen audio core, arbiter, top, SD, original OSD, board/IP, TD flow, Git commit or hardware programming was changed by this follow-up task.

Evidence under evidence/sim preserves source ZIP/SHA256, commands, UTC/PID, exits, wall time and simulator logs. Deterministic large WAV vectors are generated with `python3 tests/audio_arbiter_vectors.py`. The visual render test exports actual RTL output pixels with a deterministic synthetic stereo PCM ramp; that preview demonstrates rendering and is not a hardware screenshot or a TF-card playback capture.
